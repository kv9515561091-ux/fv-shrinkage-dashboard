# Power Query setup

The workbook ships with seven M queries already embedded. This file covers
what they do, how to load them, and how to check your work.

## Where the queries live

| Location | Use |
| --- | --- |
| Inside `fv_shrinkage_dashboard.xlsx` | Audit the M without leaving Excel, or load it to a sheet |
| `powerquery/*.pq` on the repository | Read, diff, or port the logic to Power BI |
| `scripts/analyze.py` | The pandas implementation, used to pre-populate the `PQ_*` sheets |

All three carry the same transformation. The `.pq` files are the readable
source of truth; the embedded copies are for convenience.

## Loading a query to a worksheet

1. Open `fv_shrinkage_dashboard.xlsx` and enable **Data → Queries &
   Connections**.
2. In the **Queries** pane, right-click the query (for example
   `pq_Agg_CategoryShrinkage`).
3. **Load To → Only Create Connection**, then **Close & Load To → Table** on
   the destination sheet.

Or, from a blank cell: **Data → Get Data → From Other Sources → From Microsoft
Power Query** → pick the query.

### Why the workbook does not do this automatically

`scripts/build_workbook.py` embeds the M through `Workbook.Queries.Add`, which
is reliable over COM automation. *Loading* the results requires a
`WorkbookConnection` that the Excel COM interface will not construct without a
UI, and attempting it blocks indefinitely. Rather than ship a workbook that
hangs on build, the pivot source tables are materialised in pandas
(`analyze.py`) and the PivotTables bind to those. Same logic, no hang, and the
workbook opens with live numbers on a machine that has never run the script.

## Query reference

### `pq_Load_Batches`
Types all 44 columns explicitly by name, converts the text-boolean flags
(`cold_chain_breach`, `carry_in`) to real logicals, and derives
`received_value_inr`, `shrink_pct_recalc`, `sell_through_pct`,
`arrival_condition` and `overstock_flag`.

> **Why the explicit typing matters.** An untyped numeric column arrives as
> text. Text sorts lexicographically, so a shrink column renders `9.5` above
> `12`, and a PivotTable happily reports the wrong ranking. This is the single
> most common silent failure in a Power Query pipeline feeding a pivot.

### `pq_Load_Picks`
Types the event log and adds the three measures that make a FEFO violation
interpretable:

- `rotation_depth` — how many batches deep the picker went against expiry order
- `severity` — `Minor` (≤1 day skipped) / `Moderate` (1–3) / `Critical` (>3)
- `failure_mode` — names the wrong-but-realistic rule used, because
  *"grabbed the top of the rack"* is a trainable habit and *"human error"* is not

### `pq_Agg_CategoryShrinkage`
Groups to category × perishability, keeping the six reason columns separate so
the dashboard can pivot on them as a matrix. Unpivoting first would flatten
that matrix and lose the comparison.

### `pq_Agg_FEFO_Compliance`
Compliance and mean shelf life skipped by category × zone × shift, plus the
dominant failure rule. Compliance alone is not enough: a 4-day skip on a
6-day SKU destroys the lot, while the same skip on a 35-day SKU does nothing.
Frequency and severity are reported separately.

### `pq_Agg_DailyRVP`
Daily receipts, sell-through and RVP. Drops carry-in lots so the denominator
is what the week actually bought. RVP is the residual value inside a 2-day
window, weighted by proximity to expiry (1.0 at expiry, 0.5 at the outer
edge — linear by design, so the assumption stays auditable).

### `pq_Agg_SKUBottleneck`
Per-SKU loss **ranked by rupee value**, joined to rotation metrics, with a
`primary_driver` heuristic. Ranking by percentage would point the category
team at high-rate low-value SKUs instead of the ones actually costing money.

### `pq_Load_Batches_FileVariant`
The `Csv.Document` equivalent of `pq_Load_Batches` for use outside this
workbook. Set the CSV folder to `<repo>/fv-shrinkage-dashboard/data/raw`.

## Refreshing after editing the source data

1. Replace the contents of the `Raw_Batches` / `FEFO_Pick_Log` tables (the
   data, keep the headers).
2. **Data → Refresh All**.
3. If the PivotTables are bound to loaded queries rather than the `PQ_*`
   tables, the refresh propagates automatically. If they are bound to the
   `PQ_*` tables, re-run the pipeline instead:

```bash
python scripts/generate_data.py
python scripts/analyze.py
python scripts/build_workbook.py
```

## Validating a change

The fastest check that the M and the pandas implementation still agree is to
rebuild and compare the workbook's `PQ_*` sheets against
`data/processed/PQ_*.csv`. They are generated by the same logic, so any
divergence is a regression in one of the two implementations.
